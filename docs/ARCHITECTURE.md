# 아키텍처 기획 문서

## 1. 시스템 개요 및 목표

**목표**: 로그인 후 GO 버튼 하나로 AI가 바이낸스(Binance)에서 자동매매를 수행하고, STOP 버튼으로 즉시 중단할 수 있는 개인용 웹 서비스를 만든다.

**비목표(이번 범위 밖)**:
- 다중 사용자 지원 (회원가입, 사용자별 계정 분리)
- 다중 거래소 지원 (바이낸스 단일 거래소로 시작)
- 모바일 앱 (반응형 웹 정도만 고려, 네이티브 앱은 다루지 않음)

**사용자 시나리오**: 사용자가 로그인하면 대시보드에서 현재 매매 상태(관망/포지션 보유 등), 잔고, 최근 매매 로그, AI의 판단 근거를 확인할 수 있다. GO 버튼을 누르면 자동매매 루프가 시작되어 AI가 주기적으로 시세를 분석하고 신호에 따라 주문을 실행한다. 언제든 STOP(또는 긴급 정지) 버튼을 눌러 즉시 매매를 중단할 수 있다.

## 2. 전체 아키텍처

```
[브라우저]
  ├─ 로그인 화면
  └─ 대시보드 (상태/잔고/로그/GO·STOP)
        │  HTTP / 세션 쿠키
        ▼
[Express API 서버]
  ├─ 인증 (세션 기반 로그인/로그아웃)
  ├─ GO/STOP 제어 API  ──────► [매매 상태 관리자]
  ├─ 상태/로그 조회 API              │  (RUNNING/STOPPED 영속화)
  └─ 정적 파일 서빙(프론트)          ▼
                            [매매 실행 루프]
                                  │
                    ┌─────────────┼──────────────┐
                    ▼             ▼              ▼
           [바이낸스 연동]  [AI 판단 엔진]   [리스크 관리 모듈]
           REST + WebSocket  지표+LLM 신호    손절/익절/한도/킬스위치
                    │             │              │
                    └─────► [매매 실행 엔진] ◄────┘
                                  │
                                  ▼
                          [로깅/모니터링]
                       (매매 로그, 판단 근거, 에러 로그)
```

**구성요소**:

1. **프론트엔드** — 정적 HTML/CSS/JS. 로그인 화면 + 대시보드. Express가 static serve.
2. **백엔드 API 서버 (Express)** — 인증, 세션, GO/STOP 제어 API, 상태/로그 조회 API.
3. **매매 상태 관리자** — 현재 RUNNING/STOPPED 여부를 서버 메모리 + 파일 또는 SQLite에 영속 저장.
4. **바이낸스 API 연동 레이어** — REST(잔고/주문) + WebSocket(실시간 시세) 클라이언트를 감싼 어댑터 모듈.
5. **AI 판단 엔진** — 시세/지표 데이터를 받아 BUY/SELL/HOLD 신호와 "판단 근거 텍스트"를 생성.
6. **매매 실행 엔진(Executor)** — 판단 엔진의 신호를 받아 실제(또는 모의) 주문을 넣고 결과를 기록.
7. **리스크 관리 모듈** — 손절/익절, 최대 손실 한도, 킬스위치를 실행 엔진 앞단에서 게이트키핑.
8. **로깅/모니터링** — 매매 로그, 에러 로그, 판단 근거 로그를 시간순으로 쌓고 대시보드에서 조회.

**분리 이유**: AI 판단 엔진과 매매 실행 엔진을 분리해두면, 모의투자 모드에서 AI 판단 로직만 따로 검증할 수 있다. 리스크 관리 모듈을 실행 엔진과 분리해두면, 판단 엔진이 어떤 신호를 내든 항상 동일한 안전 규칙을 통과해야 하므로 AI가 폭주해도 시스템 차원의 제어가 유지된다.

## 3. AI가 "스스로 판단"하는 부분 — 현실적 옵션

| 옵션 | 설명 | 장점 | 단점 |
|---|---|---|---|
| A. 순수 규칙 기반 | 이동평균 교차, RSI, MACD 등 기술적 지표 조합 | 설명 가능, 백테스트 쉬움 | "AI"라 부르기엔 약함, 시장 국면 변화에 둔감 |
| B. 순수 LLM 판단 | 뉴스/시세를 프롬프트로 넣고 LLM이 직접 매매 결정 | 유연한 시황 해석 | 비결정적, 환각 위험, 응답 지연, 실전 매매엔 부적합 |
| **C. 하이브리드 (권장)** | 규칙 기반 지표 전략이 1차 신호(BUY/SELL/HOLD)를 생성 → LLM은 그 신호에 대한 시황 해석/설명 텍스트 생성 + 이상 신호 필터링(극단적 변동성 시 보류 권고) 보조 → 최종 실행은 항상 리스크 게이트 통과 | 설명 가능성 + 유연성 결합, "판단 근거 표시" 요구사항과 자연스럽게 맞음 | 구현 복잡도가 A보다 높음 |

**실전 자동매매의 현실적 리스크와 완화책**:

| 리스크 | 완화책 |
|---|---|
| 과최적화 (백테스트에만 잘 맞음) | 모의투자(paper trading) 모드로 일정 기간 검증 후 실거래 전환 |
| 슬리피지 / 체결 실패 | 지정가 + 타임아웃, 최소 체결 확인 로직 |
| 바이낸스 API 장애 / 레이트리밋 | 재시도 + 백오프, 장애 시 자동 STOP(기존 포지션은 유지) |
| 급변동장 (플래시크래시 등) | 변동성 임계치 초과 시 신규 진입 중단 규칙 |
| 설정 실수·심리적 요인으로 인한 큰 손실 | 최대 손실 한도(일일/누적), 강제 손절 규칙, 수동 킬스위치 |

**안전장치**: 모의투자 모드 스위치(ENV 또는 대시보드 토글), 손절/익절 퍼센트 설정, 최대 손실 한도 도달 시 자동 STOP, 대시보드의 "긴급 정지(킬스위치)" 버튼은 GO/STOP과 별개로 항상 최우선으로 동작.

## 4. GO/STOP 상태 관리

**상태값**:
- `STOPPED` — 매매 루프 정지
- `RUNNING` — 매매 루프 동작 중
- `EMERGENCY_STOPPED` — 리스크 한도 도달로 시스템이 강제 정지한 상태. 사용자가 수동으로 리셋해야 재개 가능

**영속화**: 프로세스 재시작 후에도 상태가 남아야 하므로 단순 메모리 변수가 아니라 파일(JSON) 또는 SQLite에 저장.

**제어 흐름**: 대시보드 GO/STOP 버튼 → `POST /api/trading/start`, `POST /api/trading/stop` → 상태 갱신 → 실행 엔진의 매매 루프(인터벌/스케줄러) 시작/중단.

**엣지케이스**: 서버가 RUNNING 상태에서 재시작되면, 바로 자동 재개하지 않고 사용자에게 재개 여부를 확인받는 것이 안전하다.

## 5. 보안 고려사항

- **바이낸스 API 키**: `.env` 파일로 관리, git에 절대 커밋하지 않음(`.gitignore`에 명시). 가능하면 출금 권한 없는 API 키 발급(거래 권한만 부여), IP 화이트리스트 설정 권장.
- **로그인 인증**: 회원가입 없는 단일 계정이므로 `.env`에 아이디 + 비밀번호 해시(bcrypt)를 저장하고, 로그인 시 세션 쿠키(express-session, httpOnly) 발급. 평문 비밀번호 저장 금지. — **적용 완료** (`server/lib/auth.js`)
- **세션 관리**: 세션 만료 12시간, 로그아웃 시 세션 무효화. `NODE_ENV=production`일 때 세션 쿠키에 `secure` 플래그 자동 적용(HTTPS 전용). — **적용 완료** (`server/server.js`)
- **로그인 무차별 대입 방어**: `express-rate-limit`으로 IP당 15분에 10회로 제한. — **적용 완료**
- **HTTPS**: 배포 시 reverse proxy(Nginx/Caddy) 뒤에서 TLS 종료 권장. `NODE_ENV=production`으로 설정해야 `trust proxy`와 `secure` 쿠키가 함께 켜짐.
- **저장소 공개 범위**: GitHub 저장소는 개인 매매 전략/파라미터가 담겨 있으므로 **비공개(Private)** 유지를 권장. 공개로 두면 GitHub Pages 무료 호스팅은 가능하지만 전략 로직이 노출됨.
- **법적 범위**: 이 서비스는 본인 자금만 운용하는 개인용 도구로 설계되어 있음. 회원가입/다중 사용자 지원으로 확장하거나 타인에게 서비스를 제공하는 순간 자본시장법상 투자자문업 등 별도 인허가가 필요해지므로, 개인용 범위를 벗어나지 않는다.

## 6. 로드맵

1. **1단계 (현재)**: 로그인/대시보드 정적 목업 + 기획 문서
2. **2단계**: Express 서버 기본 골격, 세션 기반 로그인 실제 구현, GO/STOP 상태 API(매매 로직 없이 상태만 토글)
3. **3단계**: 바이낸스 API 연동 — 테스트넷/모의투자 모드로 시세 조회, 잔고 조회, 모의 주문
4. **4단계**: AI 판단 로직(하이브리드 방식) 구현, 백테스트 및 모의투자 검증
5. **5단계**: 리스크 관리 모듈 강화 후 소액 실거래 전환, 모니터링/알림(예: 텔레그램) 추가

## 7. 2단계 진행 상황 및 1차 백테스트 결과

- **서버(2단계)**: `server/`에 Express 앱 완성. 세션 기반 개인 로그인, GO/STOP/긴급정지 상태 API(`server/lib/tradingState.js`, JSON 파일 영속화)까지 동작 확인.
- **백테스트(3~4단계 선행 검증)**: `backtest/`에 바이낸스 3년치(2023-08 ~ 2026-08) BTCUSDT 1시간봉 26,280개를 수집(`fetch_data.py`)하고, 이동평균 크로스+RSI 필터 전략(`strategy.py`)을 그리드서치로 162개 파라미터 조합 탐색(`optimize.py`), 앞 2년(train)/최근 1년(test, out-of-sample)로 분리 검증.
- **1차 결과 요약** (`backtest/results/report.md` 참고): train 구간 샤프비율 1위 조합이 train에서는 +62.36%를 냈지만, 한 번도 학습에 쓰지 않은 test 구간(최근 1년, BTC가 117,394 → 63,067로 반토막난 하락장)에서는 -26.21%로 손실. 상위 10개 조합 전부 test에서 마이너스. 단순 보유 대비로도 train에서는 크게 못 미치고(+62% vs +310%), test에서는 손실 폭만 줄였을 뿐(-26% vs -46%) 수익은 내지 못함.
- **결론(v1)**: 이 단순 지표 기반 전략은 실전 투입 가능한 수준이 아니다. 다음 단계에서 전략 자체(진입/청산 로직, 포지션 사이징, 다른 지표 조합)를 개선하거나 LLM 보조 판단을 추가하고, 반드시 모의투자로 추가 검증한 뒤에만 실거래를 고려해야 한다.

### v2: 롱/숏 양방향 + 비트코인 변동성 3대 요인 반영

v1은 매수(롱)만 가능했고 시장 컨텍스트를 전혀 보지 않았다. 비트코인 변동성의 3대 요인(레버리지 청산 캐스케이드, 거시경제/유동성 환경, 얕은 유동성·뉴스 충격)을 다음과 같이 반영해 v2를 만들었다(`market_context.py`).

| 요인 | 반영 방법 |
|---|---|
| 레버리지 청산 캐스케이드 | 바이낸스 선물 펀딩비율 3년치(`fetch_funding.py`)를 병합. 펀딩비율이 특정 임계값 이상(롱 과열)이면 신규 롱 진입 회피, 반대로 낮으면(숏 과열) 신규 숏 진입 회피 |
| 거시경제/유동성 환경 | FOMC 발표일(federalreserve.gov 공개 일정, 2023~2026) 전후 1일을 매크로 리스크 구간으로 표시해 신규 진입 회피 |
| 얕은 유동성/뉴스 충격 | 24시간 실현변동성이 과거 90일 대비 상위 10%에 들면 고변동성 구간으로 보고 신규 진입 회피 |

추가로 숏 매매를 지원하도록 `backtest.py`를 확장했다(롱/숏 단일 포지션, 방향별 손절/익절, 실제 무기한 선물처럼 펀딩 정산 시점마다 펀딩비 가감).

**v2 결과 요약** (`backtest/results/report.md` 참고, v1과의 비교표 포함):

| 버전 | train 수익률 | test 수익률(out-of-sample) |
|---|---|---|
| v1: 롱온리, 필터 없음 | +62.36% | -26.21% |
| v2: 롱+숏, 3요인 필터 | +16.09% | -23.63% |

숏 매매와 3요인 필터를 추가하니 test 구간 손실 폭이 소폭 줄었다(-26.21% → -23.63%). 신규 진입을 걸러내는 필터가 일부 위험 구간을 피하는 데는 도움이 됐다는 뜻이다. **하지만 train 샤프비율 상위 10개 조합 전부 test에서는 여전히 마이너스**였다 — 필터 추가만으로는 전략을 흑자로 바꾸지 못했다. 근본 원인은 이동평균 크로스 + RSI라는 진입/청산 신호 자체의 예측력이 약하다는 데 있으며, 다음 개선은 신호 생성 로직 자체(다른 지표 조합, ML 기반 신호 등)를 바꾸는 방향이어야 할 가능성이 높다.

### v3: 신호 생성을 규칙 기반 -> ML(그래디언트 부스팅)로 교체

v2까지의 결론(신호 자체의 예측력이 약함)에 따라, 이동평균 크로스+RSI 규칙을 걷어내고 `HistGradientBoostingRegressor`가 다변수 피처(과거 수익률, RSI/MACD/볼린저밴드, 실현변동성, 거래량비율, 펀딩비율, 매크로/변동성 플래그, 시간대 주기성 — `ml_features.py`)로 향후 4~8시간 수익률을 직접 예측하도록 바꿨다(`ml_model.py`, `ml_strategy.py`). 3요인 필터는 그대로 진입 게이트로 재사용.

과최적화를 더 엄격히 막기 위해 **3분할 검증**을 도입했다(`optimize_ml.py`): 모델은 model_train(~20개월)에서만 학습하고, 진입임계값/손절익절/보유기간 같은 매매 파라미터는 model_val(~4개월)에서 자체탐색하며, test(최근 1년)는 최종 후보 단 하나만 "한 번" 검증한다.

**v3 결과**: model_val에서 탐색한 144개 조합 중 **단 하나도 플러스가 없었다**(평균 -65.7%). 가장 나은 조합조차 test에서 -27.88%로, v1(-26.21%)/v2(-23.63%)보다 오히려 나빴다.

**더 중요한 발견**: 최악의 조합은 4개월 동안 1,382번 거래해서 -94.61%를 기록했다. 원인은 모델 품질이 아니라, **v1~v3 전부가 매 거래마다 자본 전액(all-in)을 거는 포지션 사이징**을 쓰고 있었기 때문이다. 승률이 애매한(50% 안팎) 전략을 전액배팅으로 수백~수천 번 반복하면 손실이 곱셈으로 누적되어 파산에 가까워진다. 즉 지금까지 발견한 문제의 상당 부분은 "신호가 약해서"가 아니라 **"신호와 무관하게 포지션 사이징 자체가 위험했기 때문"**일 가능성이 크다.

**결론**: 신호 생성 방식(규칙기반 vs ML)을 바꾸는 것보다, **포지션 사이징(고정 비율 배팅, 켈리 기준 등)을 먼저 고치는 게 더 근본적인 다음 단계**로 보인다. 상세 결과는 `backtest/results/report_v3_ml.md` 참고.

### v4: 포지션 사이징을 리스크 기반으로 수정 + SNS 감정(공포탐욕지수) 요인 추가

v3에서 찾은 결론에 따라 두 가지를 동시에 반영했다.

**1) 포지션 사이징 수정** (`backtest.py`): 매 거래 전액배팅을 없애고, 손절에 걸렸을 때 자본의 `risk_per_trade_pct`(기본 1%)만 잃도록 포지션 크기를 역산하는 방식으로 바꿨다(`notional = cash * risk_per_trade_pct / stop_loss_pct`, 레버리지 없이 보유 현금 한도 내). 투자되지 않은 현금은 별도로 추적해 유휴 자본으로 남긴다.

**2) SNS/시장심리 요인 추가** (`fetch_sentiment.py`, `market_context.py`): 원 요청은 SNS 게시글을 직접 감정분석하는 것이었지만, 3년치 원문 텍스트를 수집·분류하는 건 이 프로젝트 범위에서 비현실적(X/Twitter API 유료·제한적, 대량 NLP 처리 비용)이라 판단해, 소셜 여론·설문·모멘텀을 종합하는 무료 공개 지표인 **Crypto Fear & Greed Index**를 대체 데이터로 썼다. Extreme Fear/Fear = 부정(0), Neutral = 중립(1), Greed/Extreme Greed = 긍정(2)로 매핑하고, 요청하신 대로 점수가 높으면(긍정) 롱을, 낮으면(부정) 숏을 우대하도록 진입 필터에 반영했다(`allow_long_entry`는 sentiment_score>=1, `allow_short_entry`는 sentiment_score<=1을 추가 조건으로 요구). ML(v3) 피처에도 `sentiment_score`를 추가해 모델이 직접 학습하도록 했다.

**결과 비교**:

| 버전 | 방식 | test(out-of-sample) |
|---|---|---|
| v2 (전액배팅) | 롱+숏, 규칙기반+3요인 필터 | -23.63% |
| v2 (수정 후) | 롱+숏, 규칙기반+4요인(감정 포함) 필터, 리스크기반 사이징 | **-4.22%** |
| v3 (전액배팅) | ML+3요인 필터 | -27.88% |
| v3 (수정 후) | ML+4요인(감정 포함) 필터, 리스크기반 사이징 | **-10.61%** |

포지션 사이징을 고치니 손실 폭이 큰 폭으로 줄었다(v2: -23.63%→-4.22%, v3: -27.88%→-10.61%). 다만 **v3의 파라미터 탐색 구간(model_val) 144개 조합 중에서는 사이징을 고친 뒤에도 여전히 플러스가 하나도 없었다**(평균 -48.7%, 이전 -65.7%에서 개선됐지만 부호는 그대로 마이너스). 즉 사이징 문제와 신호 품질 문제는 서로 별개였고 **둘 다 실재했다** — 사이징을 고쳐서 "덜 위험하게 잃는" 상태는 됐지만 아직 "이기는" 전략은 아니다. 감정 요인 추가만으로 흑자 전환에 이르지도 못했다.

**결론**: v2(규칙기반, -4.22%)가 지금까지 만든 것 중 가장 손실이 적은 버전이다. 0%(손익분기)에 가장 가깝다는 점에서 추가 개선의 출발점으로 삼을 만하다. 상세 비교는 `backtest/results/report.md`, `backtest/results/report_v3_ml.md` 참고.

### v5: 분할진입(1~2% 리스크 법칙 + 선진입/추가진입) + 레버리지 검토

사용자가 실전에서 쓰는 방식을 반영: 손절 -2%를 기준으로 목표 포지션의 20~30%만 먼저 진입하고,
이후 진입봉의 고점(롱)/저점(숏)을 넘어서는 "확인"(지지선 반등이든 추세 돌파든 결과적으로 진입가
방향의 새 극값을 만든다는 공통점으로 단순화)이 나오면 나머지를 추가 진입한다(`backtest.py`의
`initial_entry_fraction`/`confirm_window`). 확인이 안 나오면 초기 물량만으로 관리한다.
신호 로직은 v2에서 이미 골라낸 값(short=30/long=100/rsi_ob=75/rsi_os=30)을 그대로 고정해서
분할진입 자체의 효과만 분리해서 봤다(`optimize_v5.py`).

**레버리지에 대해**: "1~2% 리스크 법칙"을 그대로 적용하면 목표 포지션 크기는
`자본 x 리스크% / 손절%`로 정해진다. 사용자가 말씀하신 손절 -2%, 리스크 1% 조합을 넣으면:

| 손절폭 | 필요 포지션 비율(자본 대비) | 레버리지 필요 여부 |
|---|---|---|
| 0.5% | 200% | 필요 |
| 1.0% | 100% | 경계 |
| **2.0%(요청하신 값)** | **50%** | **불필요** |
| 3.0% | 33% | 불필요 |

즉 리스크 법칙을 제대로 지키는 한, 손절폭이 1%보다 넓으면(요청하신 2%는 여기 해당) **레버리지를 켜고 끄고가 결과에 전혀 영향을 주지 않는다** — 왜냐하면 이 사이징 공식 자체가 "손절에 걸렸을 때 자본의 1%만 잃는" 포지션 크기를 이미 계산해주기 때문에, 레버리지는 그 크기를 만드는 데 필요한 증거금을 줄여줄 뿐 손익 자체를 바꾸지 않는다. 레버리지가 실제로 의미를 가지려면 손절폭이 1%보다 좁아야 하는데(예: 0.5%), 1시간봉 기준 그렇게 좁은 손절은 잡음(noise)에 자주 털릴 위험이 커서 이번 실험에는 포함하지 않았다. 레버리지를 더 써서 리스크 법칙보다 큰 포지션을 잡는 건 "1~2% 리스크 법칙" 자체를 깨는 것이므로 권장하지 않는다.

**결과** (`backtest/results/report_v5_scaled_entry.md` 참고, 20개 조합 전수 비교):

| | 초기비율 | 확인창 | 손절/익절 | train 수익률 | test 수익률 |
|---|---|---|---|---|---|
| 분할진입 없음(v2) | 1.0 | - | 3%/8% | +7.7% | -4.22% |
| 분할진입 최적(train 샤프 1위) | 0.3 | 4봉 | 3%/8% | +6.27% | **-2.57%** |

**같은 손절/익절 조합끼리 비교했을 때, 분할진입을 켠 경우가 4쌍 전부에서 예외 없이 test 손실을 줄였다**(-4.75%→-1.5%, -4.22%→-2.57%, -3.3%→-2.38%, -3.39%→-0.09% 등). 지금까지 만든 모든 버전 중 test 결과가 가장 손익분기에 가깝다(-2.57%). 분할진입이 실제로 유효한 개선이었다는 뜻이다.

**남은 과제**: 여전히 마이너스라 실전 투입 가능 단계는 아니다. 다음으로 시도해볼 만한 것은 지지선/저항선을 실제 스윙 고점·저점 기반으로 더 정교하게 정의하는 것, 또는 v3(ML)에도 같은 분할진입을 적용해보는 것이다.

### 자본금 증식(100만원 -> 1억) 목표와 레버리지/회전율에 대한 실증

사용자가 최종 목표(소자본을 크게 불리는 것)를 위해 레버리지를 적극 활용하고, 굳이 오래 들고 있지 않고 짧게짧게 수익을 내는 방식도 괜찮다는 의견을 주어 두 가지를 직접 실험했다.

**1) 리스크%(=레버리지에 해당)를 키우면?** v5 최적 조합(손절 3%/익절 8%/30% 선진입)을 고정하고 `risk_per_trade_pct`만 1%→10%로 늘려가며 비교(`optimize_v5.py`의 신호+엔진 재사용, 수동 스윕):

| risk_per_trade_pct | train 수익률 | train MDD | test 수익률 | test MDD |
|---|---|---|---|---|
| 1% | +6.27% | -4.07% | -2.57% | -3.61% |
| 2% | +12.59% | -8.00% | -5.17% | -7.15% |
| 3% | +18.95% | -11.82% | -7.78% | -10.60% |
| 5% | +20.18% | -11.93% | -9.13% | -11.89% |
| 10% | +22.68% | -13.13% | -12.56% | -15.90% |

train(양의 edge가 있던 구간)에서는 베팅을 키울수록 수익도 커지지만, **test(진짜 out-of-sample)에서는 베팅을 키울수록 손실도 같은 비율로 커진다.** 레버리지/베팅 크기는 edge를 만들어내지 않고 있는 edge를 증폭만 시킨다는 걸 숫자로 확인한 것 — 지금처럼 test edge가 아직 마이너스인 상태에서 레버리지를 키우는 건 목표(자본금 증식)에 역행한다.

**2) 짧게짧게 수익실현(퀵 스캘프)은?** 익절폭 2~4% + 최대보유 12~48시간 조합 32개를 정식 탐색(`optimize_v6.py`). 결과는 `backtest/results/report_v6_quick_scalp.md` 참고 — **전부 기존 최고 기록(-2.57%)보다 나빴다**(예: 최대보유 48봉 제한 시 -3.3%로 악화). 이 데이터에서는 보유시간을 강제로 제한하기보다, 좁은 손절을 유지한 채 목표가까지 충분히 들고 가는 편이 더 낫다는 결론이 나왔다.

**결론**: 100만원→1억이라는 목표 자체는 타당하지만, 그 경로는 "레버리지/회전율로 속도를 내는 것"이 아니라 **"양의 기대값을 가진 전략을 먼저 확보하는 것"**이어야 한다. edge가 확인된 뒤에 리스크%(레버리지 포함)를 얼마나 키울지 논의하는 순서가 맞다.
